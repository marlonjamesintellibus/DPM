8 shapes, and statuses as rules

Every DPM machine is one of the 7 shapes the Atlas map already uses, or 1 new one, Stage. A shape that is checked once holds for every machine built from it. Statuses are not machines at all; they are rules over machines.

Switchfrom Atlas

On or off, or one of a few options, until someone or a timer flips it.

OffOn
  • Off → On: turn on
  • On → Off: turn off
  • Some are a choice of a few options, like a set status (On track, At risk, Off track).
  • Some stay On only until a time, like on leave today or a snooze.
  • Some are one way: once On, never Off, like a missed reply target.
  • Some wait before they flip, like Stalled after N quiet days.

11 machines, such as Routing an item, On leave today, First reply target, Escalation level, Set status and 6 more

Thingfrom Atlas

A record that exists until it is closed or deleted.

DraftLiveGone
  • Draft → Live: publish or send
  • Live → Gone: delete or retention ends
  • A capture is Live from the start and is never edited (A5.6).
  • When a Thing is Gone, everything it owns goes with it.

3 machines, such as Capture, Briefing, Pulse response

Membershipfrom Atlas

A person's place in something shared: a team, a project, a contract seat.

InvitedRequestedMemberLeft
  • Invited → Member: accepts
  • Requested → Member: approved
  • Member → Left: leaves or removed
  • A role’s scope comes from Memberships (A7.1).
  • Only Members see what’s inside.

3 machines, such as Team membership, Role on a project, Seat

Askfrom Atlas

A question that gets one answer: from Atlas to a person, or from a rule to an owner.

AskingYesNoTimed outWithdrawn
  • Asking → Yes / No: a person answers
  • Asking → Timed out: deadline
  • Asking → Withdrawn: the cause is gone
  • It ends exactly once. An answer after the end changes nothing.
  • A deadline, or a way to withdraw it, means it never waits forever.
  • Only a person with the right role can answer (P5).

16 machines, such as Atlas's question, Extracted update, Same as an existing entry, Suggestion, Approval and 11 more

Jobfrom Atlas

Work that may wait, fail and try again: reading a message, applying an update, running an approved action.

WaitingWorkingDoneFailedCancelled
  • Waiting → Working: its turn
  • Working → Done: finished
  • Working → Waiting: error, try again later
  • Working → Failed: gave up
  • Every try reuses one ID, so the work never happens twice (C14.5).

4 machines, such as Capture processing, Apply update, Atlas action, Handover

Presencefrom Atlas

Here only while it keeps checking in: a customer who talks to us, a data feed, a person who checked in.

HereQuietGone
  • Here → Quiet: no check-in for a while
  • Quiet → Here: heard again
  • Quiet → Gone: quiet too long
  • A check-in restarts its timer.
  • Quiet is what shows as "stale, as of 9:10am" (P11).

A limit that refills, like a person’s working week.

OpenUsed up
  • Open → Used up: limit reached
  • Used up → Open: the week ends
  • In Atlas a used-up Allowance refuses new work. DPM only warns (A10.1 "Over 100% allocated" is a Warning). Open.

8 rules every machine follows

These replace special cases. Rules 1 to 3, 6 and 7 come from the Atlas map; 4 and 5 are DPM principles; 8 came out of the checker. Stories and decisions refer to them by number.

  1. One thing, one machine. Each update, approval, check-in and inbox item has one machine. Its state is the only truth; Chat, Inbox, Dashboard and Table only show it (P7).
  2. Only drawn arrows. A machine moves only along an arrow in its picture. Anything else is refused and changes nothing (C0).
  3. Nothing gets stuck. Every waiting state has a timer or a named way out. An assumption needs a check-by date; an inbox item closes when its cause is gone.
  4. Atlas asks, people answer. Atlas only creates Asks: proposals, questions, approvals. Only a person with the right role answers them (P5).
  5. Statuses are rules, not states. No machine stores a calculated status. A set status is a Switch with a reason Ask beside it (P6, P9).
  6. Once only. Every update and action carries an ID. A second copy, from another channel or a retry, changes nothing (C14.5).
  7. You see only what’s yours. Scope comes from Memberships. Counts-only facts are separate queries, never lists with names hidden (A7, P10).
  8. Permission is checked when it runs. An approval counts only while the approver still holds the role. If not, it goes back for approval. Found by the checker; not in C5 yet.

Decisions for you

First what this design changes from the knowledge base, then what the checker raised, then the open questions already in Part F.

Changes this design makes

  • Every DPM machine is one of the 7 Atlas shapes, plus 1 new shape, Stage, for things that move through named stages.
  • Statuses are not machines. Thread, project, area and overall status are rules over machines. C0 already says this; the map makes it the only option.
  • Inbox items, approvals, reasons, check-ins, assumptions and dependencies are all Asks, so they share one set of checks: each ends once, and each has a deadline or a way to withdraw it.
  • A seat is a Membership (proposed, approved, filled, released), not a pipeline.
  • Customer quiet days and data freshness are Presence: here only while they keep checking in.
  • Delegating an inbox item withdraws it and opens a new one for the other person, instead of a "delegated" state (rule 1).

Raised by the checker and the mapping

  • F3, set status expiry: under the rule in C3 today, a set status can outlive finished work. "On any change" or "when done" fix it; a 7 day expiry does not.
  • Can an owner still give a reason after the work is Done, or should that inbox item close when the work finishes?
  • Permission when it runs (rule 8): without it Atlas can act on an approval that no longer counts, or wait forever.
  • The same message from 2 channels: apply once per ID (rule 6). Should Atlas also spot the copy before asking twice?
  • Keep the stage when an opportunity is lost, so it fits the Stage shape and reports can say where it was lost.
  • Does a missed first reply keep counting against care replies after the reply arrives?
  • Assumptions need a check-by date, or they can wait forever (rule 3).
  • Over 100% allocated: Atlas Allowances refuse work; DPM only warns. Keep warning?

How every model is checked

  • Each shape on its own first. The Atlas map checks each of its 7 shapes once in TLA+. DPM can reuse those checks and add one for Stage.
  • Then together. Each DPM model joins a few machines and checks the rules between them, such as a set status and its reason, or an approval and the action it unlocks.
  • Small enough to finish. 2 or 3 of everything. Every model above finishes in under a second.
  • Planted bugs. Every check must fail on a bug planted for it, so a passing check is not a check that tests nothing.
  • Stories. The checker may take only a story's moves, in order, and every row must match as written.
  • TLC next. Once Java is installed, run the same specs in TLC and compare; any difference means the JavaScript port and the TLA+ have drifted.
